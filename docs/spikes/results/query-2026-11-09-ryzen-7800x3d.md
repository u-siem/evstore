# Query benchmarks: raw results, 2026-11-09

- **Machine**: AMD Ryzen 7 7800X3D, Windows 11, Samsung 980 PRO (NVMe), release build.
- **Command**: `cargo bench --bench query` (defaults: 20 flushed segments of 20,000 rows, plus 20,000 rows left in the WAL buffer; median of 7 runs after one warm-up).
- **Data**: 420,000 synthetic sshd-like records: `host` (50 values) and `user` (201 values) as dictionary strings, `src` (IP), `port`, `event_id` (8 values), `bytes`, a mostly unique mixed-case `message` (plain string), and a `blob` (bytes) on 10% of rows.

| Query | Rows | Before | After |
|---|---:|---:|---:|
| eq dict (host), asc, all | 8,309 | 69.08 ms | 66.37 ms |
| eq dict rare (user=admin), asc, all | 8,268 | 74.25 ms | 67.70 ms |
| eq dict, desc, limit 100 | 100 | 1.91 ms | 1.03 ms |
| true, desc, limit 100 | 100 | 18.02 ms | 0.19 ms |
| contains plain (message) | 8,268 | 117.81 ms | 92.09 ms |
| glob plain `*for admin*` | 8,268 | 385.97 ms | 92.07 ms |
| `@any` contains admin | 8,268 | 101.72 ms | 108.78 ms |
| range int (port 1000..1100) | 657 | 63.09 ms | 60.56 ms |
| or(eq dict, bytes exists) | 49,577 | 105.94 ms | 102.48 ms |
| cidr /24 (src) | 1,670 | 62.66 ms | 59.15 ms |
| agg: count, no filter | 1 group | 1.08 ms | 1.11 ms |
| agg: count where host=web07 | 1 group | 15.91 ms | 14.26 ms |
| agg: count by event_id (int) | 8 groups | 57.23 ms | 28.09 ms |
| agg: count by host (dict) | 50 groups | 34.54 ms | 27.36 ms |
| agg: sum bytes by src (IP) | 65,430 groups | 255.92 ms | 203.89 ms |

"Before" is the code before the scan and aggregation changes listed in the changelog; "After" includes them.

## Observations

- Matches are spread over every chunk, so most searches decode every column of every chunk: about 60 ms for 420,000 rows is the floor here. Counting with the same filter (only the filtered column and timestamps) takes 14 ms, so late materialization is most of the cost.
- `range int` and `cidr` cannot prune: random ports and IPs make every chunk's zone map cover the whole domain.
- Comparing builds of different crates is unreliable: the same evstore code ran about 20% slower when built as a path dependency than as a git dependency of another crate (identical flags), most likely code layout. Compare runs of one build setup only.

## Round 2: lazy planning, row-level postings

Same machine, data and command. The bench now opens a fresh store before each query: "first" is that query's cold run (dictionaries and postings decoded on demand), "median" the warm runs after it.

| Query | Round 1 (median) | Round 2 first | Round 2 median |
|---|---:|---:|---:|
| eq dict (host), asc, all | 66.37 ms | 63.86 ms | 57.18 ms |
| eq dict rare (user=admin), asc, all | 67.70 ms | 62.03 ms | 55.10 ms |
| eq dict, desc, limit 100 | 1.03 ms | 0.93 ms | 0.72 ms |
| true, desc, limit 100 | 0.19 ms | 0.26 ms | 0.18 ms |
| true, storage, all (materialize all 420,000) | — | 276.94 ms | 272.95 ms |
| agg: count where host=web07 | 14.26 ms | 1.99 ms | 0.71 ms |

- Lazy planning matters for cold queries and memory: a newest-first query with a limit decodes nothing from segments it never reaches. In warm runs, dictionaries and postings are already cached, so the gain is small.
- Exact postings answer `count where host=web07` from bitmaps (20× faster) and skip `eval` and the filter column for exactly indexed filters.
- Full materialization costs about 0.65 µs per record. Pre-sizing record field vectors saved about 5%; the per-value field-name `String` that `Record` requires accounts for much of the rest.

End to end (`usiem-query`, `cargo bench --features evstore --bench evstore`, 200,000 events, patched to this evstore):

- `host:web07 | tail 100`: 58 ms → 1.4 ms (read newest-first, stop after 100).
- Raw adapter search (materialize + decode every event): 2.04–2.16 µs → 1.56–1.76 µs per event with the flat-field decode path (two runs each).
- `sort … | head n` now holds at most `n` events; on this data the sort was never the bottleneck, so its time is unchanged (decode dominates).

## Round 3: projection

`Query::fields` decodes and emits only the named fields.

| Query | Round 3 first | Round 3 median |
|---|---:|---:|
| true, storage, all (materialize all 420,000) | 309.69 ms | 272.92 ms |
| true, storage, all, fields [host] | 61.25 ms | 58.89 ms |

End to end (`usiem-query`): a `stats` the store can't answer itself now streams events that carry only the fields the pipeline reads, without raw data or origin. Both columns are built against a local evstore checkout (round 2 at `5f7dde7` vs round 3), 7 runs each:

| Query | Round 2 | Round 3 |
|---|---:|---:|
| `host:web07 \| stats dc(user.name)` | 33.52 ms | 8.26 ms |
| `* \| sort @timestamp \| head 50000 \| stats values(event.code)` | 70.51 ms | 23.93 ms |
| `event.code:* \| where source.port>1024 \| stats dc(user.name) by host` | 309.26 ms | 192.85 ms |
| `443 \| stats count by event.code` | 333.68 ms | 290.67 ms |
| `admin \| stats count by host` | 63.88 ms | 63.91 ms |

- Skipping the origin as well as the raw data was worth 13–25% on the projected rows (measured with and without it).
- `admin | stats …` doesn't improve: evstore narrows it to 4,100 rows, and evaluating `@any contains` dominates.
- `443 | stats …` still decodes every field of every event: a bare term reads all fields, and every event has an IP field that the term might match as text.
- Queries whose events are the result are unchanged (rerun with 15 runs where a single run looked off).
